# EX07 纯内存 Optuna 性能基准设计

## 1. 背景

EX07 预注册最少完成 1024 个 Trial，最多完成 4096 个 Trial，并设置两小时墙钟上限。正式运行在 7248.97 秒内完成 608 个 Trial，因墙钟上限停止。归档时间戳和当前设备的只读诊断表明，平均每个八 Trial 批次耗时 95.23 秒，其中绝大部分耗在 Optuna 通过 SQLite 逐项持久化 94 个参数和 10 个结果属性；后续同等规模的八进程回测批次只需约 0.41 秒。

本设计只验证将 Optuna 运行态存储替换为纯内存后的端到端极限吞吐。它是工程性能实验，不是新的策略研究，不改变 EX07 的冻结事实和结论。

## 2. 目标

1. 为现有 EX07 搜索管线增加显式纯内存存储能力。
2. 保持候选因子、94 维参数化、TPE 配置、投影规则、目标函数、批次大小、进程数和 ask/tell 顺序不变，隔离存储层这一变量。
3. 分别完成 16、256 和 1024 个 Trial 的工程基准。
4. 量化参数生成、并行评估、结果写回和总运行时间。
5. 报告相对正式 EX07 的加速倍数，并估算完成 4096 个 Trial 所需时间。

## 3. 非目标

- 不覆盖或续跑 `experiments/0824_EX07`。
- 不修改 EX07 已跟踪的协议、冻结策略、研究文档或产物。
- 不读取 2026 数据，不执行冻结或留出验收。
- 不压缩 91 个原始权重参数，不改为随机种子或潜变量表达。
- 不删除 Trial 结果属性，不简化八窗口回测指标。
- 不实现崩溃恢复、SQLite 回写或周期检查点。
- 不把性能基准结果解释为新的策略 PASS/FAIL 证据。

## 4. 约束与不变量

- 选择样本截止日固定为 `2025-12-31`。
- 候选身份必须逐项等于 EX06 的 91 项候选及其协议哈希。
- Trial 0 必须精确重放 EX04，目标值为 0。
- 使用 Optuna 4.9.0、`TPESampler(seed=20260824, n_startup_trials=256, multivariate=True, group=False, constant_liar=True)`。
- 一个 Trial 仍包含 `active_factor_count`、91 个 `raw_weight`、`enter_threshold` 和 `exit_gap`。
- 批次大小为 8，Joblib 使用 `loky` 8 进程，`inner_max_num_threads=1`。
- 主进程按 Trial 编号顺序 ask，并按 Trial 编号顺序 tell。
- 不使用 Git worktree；在当前 `master` 上开发并保护已有修改。

## 5. 架构

### 5.1 存储创建边界

将 Study 创建拆分为明确的存储模式：

- `sqlite`：保留现有 EX07 恢复路径和协议校验，行为不变；
- `memory`：使用 Optuna `InMemoryStorage`，不创建、读取或验证 `runtime/optuna.db`。

正式 EX07 入口继续显式使用 `sqlite`。独立性能基准入口只使用 `memory`，从而避免历史入口因默认值变化而静默改变行为。

### 5.2 基准入口

新增独立命令行入口，职责仅包括：

1. 调用现有 `prepare_selection_inputs`，加载并校验截至 2025-12-31 的数据、EX04 基线和 EX06 候选身份；
2. 创建新的纯内存 Study；
3. 注入 EX04 为 Trial 0；
4. 固定完成指定数量的 Trial；
5. 输出结构化性能摘要；
6. 退出而不冻结策略、不加载留出数据、不写 EX07 档案。

入口接受 `--trials`，仅允许用于工程基准。正式交付依次运行 16、256、1024。基准 JSON 写入 Git 忽略的 `outputs/benchmarks/`，同时在终端打印实际文件路径。该目录只保存当前设备性能证据，不纳入研究档案。

### 5.3 计时

`run_study_batches` 增加可选的批次计时收集，不改变默认返回语义。每批至少记录：

- `ask_and_project_seconds`：创建 Trial、建议94个参数并投影策略；
- `parallel_evaluate_seconds`：Joblib 批次评估；
- `tell_and_attrs_seconds`：写入10个用户属性并完成 tell；
- `batch_total_seconds`。

汇总记录总和、均值、中位数、P95和最大值。16 Trial 基准可观察进程启动；256 Trial 覆盖完整随机启动区间；1024 Trial 覆盖 TPE 历史增长后的稳定吞吐。

## 6. 数据流

```text
Git 跟踪的 2020—2025 数据与 EX04/EX06 档案
                    |
                    v
       prepare_selection_inputs（只读）
                    |
                    v
       Optuna InMemoryStorage + TPE
                    |
          每批 ask/project 8 项
                    |
                    v
          Joblib 8进程并行评估
                    |
                    v
        主进程顺序 attrs/tell（内存）
                    |
                    v
     outputs/benchmarks/*.json（工程证据）
```

## 7. 错误处理

- 若选择数据包含 2026 日期，立即失败。
- 若候选身份、协议哈希或 Trial 0 等价性失败，立即停止，不运行大基准。
- 若工作进程结果缺失、重复或编号未知，沿用现有全批失败规则。
- 内存模式中断后不恢复，重新执行整个基准；输出文件只在成功完成后原子落盘。
- 性能结果必须记录 Python、Optuna、Joblib、CPU逻辑核心数、Trial 数、进程数和实际命令。

## 8. 测试

采用测试驱动实现，至少覆盖：

1. 内存模式创建 `InMemoryStorage`，且不创建 SQLite 文件。
2. SQLite 模式继续使用现有数据库路径，正式入口行为不变。
3. 小型固定协议下，内存与 SQLite 的参数投影、目标值和排名一致。
4. 批次计时字段完整、非负且批次数正确。
5. 基准入口不调用冻结或2026留出路径。
6. Trial 0 目标值严格为0。
7. 输出路径位于 Git 忽略目录，成功结果包含环境与吞吐指标。

实现后运行 Optuna 相关聚焦测试，再运行项目唯一快速测试命令；性能基准不作为单元测试的一部分。

## 9. 性能验收

交付必须报告：

- 16、256、1024 Trial 各自总耗时；
- 每阶段耗时及占比；
- Trial/小时；
- 相对 EX07 正式运行 301.95 Trial/小时的加速倍数；
- 按1024实测吞吐估算4096 Trial所需时间；
- Trial 0 等价性和选择截止日；
- 基准是否完整完成以及任何异常。

1024 Trial 必须完整结束才能宣称达到原协议最低搜索数量。性能结果不设预先保证的加速倍数，避免用期望替代实测。

## 10. 交付边界

本轮交付代码、测试、设计和当前设备基准报告，不启动新一轮正式策略研究。若纯内存结果满足预期，后续再单独预注册新的研究实验；若仍不足，再讨论参数压缩、流水线调度或指标快速路径，不能把多项优化混入本轮归因。
