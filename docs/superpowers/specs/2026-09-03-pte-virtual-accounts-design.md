# PTE 虚拟账户与完整基线设计

日期：2026-09-03  
开发分支：`codex/pte-virtual-accounts`

## 1. 目标

在 `paper_trading_engine`（PTE）中增加多个相互隔离的虚拟账户，让不同冻结策略可以在同一套前瞻行情上独立运行、记账和比较。Futu 模拟账户继续作为唯一渠道验证账户，用于验证真实委托、订单状态和成交回报链路。

同时收敛策略身份：执行规则合并入基线。一个冻结基线包含信号、仓位、定价、费用和虚拟成交规则，运行时只选择一个基线版本，不允许基线与独立执行规则自由组合。

## 2. 已确认边界

- PTE 与 `czsc_trader` 是同仓库并列的独立 Python 包。
- PTE 继续通过 CLI 调用 `czsc-trader advice run`，不导入 `czsc_trader.*`。
- 每个虚拟账户只引用一个不可变的 `baseline version + SHA-256`。
- Futu 模拟账户只有一个；同一标的上的多个策略不同时提交到 Futu，避免净持仓破坏策略归因。
- 内部虚拟账户用于公平策略观察；Futu 账户用于渠道链路验证，两类结果分别展示。
- 自动交易继续允许在缺少实时行情权限时运行。订单定价完全由项目生成，渠道端自动调价保持关闭。
- 暂停只阻止新订单，仍然完成已有订单的状态同步与虚拟结算；撤单继续需要二次确认。
- 行情发布和策略决策在交易日 19:00 后进行；订单状态与成交回报维持短周期轮询。
- 首版完成 P0：完整基线、虚拟账户账本、自动运行、观测页面、干预能力和必要迁移。不扩展到实盘。

## 3. 完整基线

### 3.1 身份模型

`configs/rule_baselines/` 是唯一生产策略注册表。新增完整基线时：

- 复制候选 143 的信号、regime、权重和阈值；
- 在基线文件内增加 `execution` 对象；
- 生成新的基线版本和 SHA-256；
- 将原 `baseline_20260901` 归档但保持内容和哈希不变；
- 将新的完整基线设为活动版本。

`configs/execution_policies/` 和 `experiments/0902_EX02/` 保留为历史证据。生产 advice、回测和 PTE 不再解析独立执行规则注册表。

### 3.2 execution 对象

完整基线中的 `execution` 至少固定以下内容：

```json
{
  "entry": {
    "order_type": "LIMIT",
    "limit_family": "previous_close_ratio",
    "limit_parameter": 0.0,
    "price_rounding": "floor"
  },
  "exit": {
    "order_type": "LIMIT",
    "limit_ratio": 0.2,
    "price_rounding": "nearest_half_up"
  },
  "instrument": {
    "symbol": "588080.SH",
    "market": "CN",
    "asset_type": "etf",
    "price_tick": 0.001,
    "lot_size": 100,
    "maximum_order_quantity": 1000000,
    "price_limit_ratio": 0.2
  },
  "capital": {
    "mode": "full_available_cash",
    "fee_rate": 0.0005,
    "target_scope": "entry_cycle"
  },
  "virtual_fill": {
    "buy_open": "open_at_or_below_limit",
    "buy_intraday": "low_strictly_below_limit",
    "touch_only": "uncertain_unfilled",
    "sell": "marketable_limit_at_open",
    "liquidity_check": "diagnostic_only"
  }
}
```

注册表和解析器校验这些字段完整、数值有效，并校验 `exit.limit_ratio == instrument.price_limit_ratio`。任何缺失、未知枚举或标的不匹配均停止生成 advice。

### 3.3 持仓周期目标

“使用全部账户资金”在每个 `0 -> 1` 持仓周期开始时只计算一次：

```text
cycle_target_quantity = floor(
    available_cash / (buy_limit * (1 + fee_rate)) / lot_size
) * lot_size
```

PTE 持久化 `cycle_target_quantity`。未成交或部分成交后，只补齐 `cycle_target_quantity - actual_quantity`；价格改善产生的剩余现金不触发连续加仓。目标仓位回到 0 且持仓清零后，本周期结束；下一次入场重新计算目标数量。

超过单笔最大申报数量时拆分为不超过 1,000,000 份的子订单。每个子订单仍使用同一决策身份派生出的唯一意图身份。

## 4. advice 契约

新增 `advice.v3`，它只暴露完整基线身份：

```json
{
  "contract_version": "advice.v3",
  "baseline": {"version": "...", "sha256": "..."},
  "decision_id": "...",
  "signal_date": "YYYY-MM-DD",
  "valid_session": "YYYY-MM-DD",
  "actual_quantity": 0,
  "cycle_target_quantity": 0,
  "target_quantity": 0,
  "delta_quantity": 0,
  "order": null
}
```

- 删除可独立选择的 `execution_policy` 身份。
- CLI 增加可选的 `--cycle-target-quantity`，PTE 在周期建立后每次调用都传入持久化值。
- 首次入场未提供周期目标时，由 advice 按完整基线计算并返回。
- `decision_id` 覆盖完整基线身份、账户状态、信号日期、有效交易日、周期目标和订单字段。
- `advice.v1/v2` 只保留必要的历史兼容测试；PTE 生产链路切换到 `advice.v3`。

## 5. 虚拟账户领域模型

每个虚拟账户包含：

- `account_id`：稳定且唯一；
- 中文名称；
- 基线版本和哈希；
- 标的；
- 创建时间、观察起始交易日；
- 初始资金、可用现金、冻结资金、持仓数量、持仓成本和总资产；
- 当前持仓周期目标；
- 运行开关；
- 最近结算交易日和最近决策身份。

账户创建时未显式给出初始资金则使用10万元默认值；显式给出的初始资金必须大于零。不同账户的资金与订单完全隔离。收益比较使用净值比例；页面同时展示各自观察期，并只在共同覆盖区间计算横向比较指标。

首个虚拟账户使用新的完整候选 143 基线，账户 ID 为 `baseline-143`，中文名称为“候选143”。每个虚拟账户默认初始资金为 `100,000.00` 元，可在创建时显式覆盖；Futu 模拟账户总资产不因此改变。旧版自动创建的100万元账户仅在尚无交易生命周期记录时安全迁移，已有记录则拒绝静默改账。后续 Range 候选只有冻结成新的完整基线后才能创建账户。

## 6. 虚拟订单与成交

虚拟订单同样遵守 `intent -> order -> fill` 链路：

1. advice 产生下一交易日有效的 DAY 限价单；
2. PTE 先持久化意图和订单；
3. 下一交易日 19:00 后，未复权执行日线发布完成；
4. 虚拟成交模型读取该交易日 OHLC 结算订单；
5. 明确模型成交后才改变现金和持仓；
6. DAY 订单未成交则过期，目标仍有效时由下一次 advice 生成新订单。

买入成交规则：

- `open <= limit`：按开盘价全额模型成交；
- `open > limit` 且 `low < limit`：按限价全额模型成交；
- `low == limit`：状态记为“触价但成交不确定”，按未成交处理；
- `low > limit`：未成交。

卖出使用保护性限价：当开盘价不低于卖出限价时按开盘价成交；无法证明可成交时保持持仓并在下一交易日重试。

首版不根据日线或30分钟成交量虚构部分成交。订单数量占当日成交量的比例作为流动性诊断字段；模型成交与 Futu 明确成交分别标记来源。

费用按成交金额乘以基线内 `fee_rate` 扣减。所有金额使用十进制定点计算，持仓数量必须为整数且符合整手规则。

## 7. 运行协调

PTE 保留现有 Futu 引擎并新增虚拟账户协调器：

- Futu 引擎负责一个渠道验证账户；
- 虚拟账户协调器负责 N 个内部账户；
- 调度器共享行情发布状态，但账户账本相互隔离；
- Futu 查询、连接或提交失败只影响渠道验证账户，不阻止虚拟账户结算和生成决策；
- 19:00 后先发布并验证行情，再结算上一有效交易日的虚拟订单，最后为下一交易日生成新决策；
- 同一行情数据身份、账户和决策只能处理一次；
- 单个虚拟账户失败时记录账户级告警，其余账户继续运行；
- 行情或完整基线身份校验失败时，不结算、不生成新单。

渠道连续失败采用有上限的指数退避，恢复后重置退避。相同错误在退避窗口内聚合计数，只保留首次、计数更新和恢复事件，避免亚秒级重复事件淹没运行日志。

一个可配置的虚拟账户可标记为 Futu 参考策略。该标记只用于页面并排比较，不会把虚拟订单自动复制到 Futu；Futu 委托仍由现有渠道引擎独立生成、提交和对账。

## 8. 存储

在现有 SQLite 运行库中新增独立表：

- `virtual_accounts`
- `virtual_intents`
- `virtual_orders`
- `virtual_fills`
- `virtual_snapshots`

全部业务表以 `account_id` 分区，并设置以下唯一约束：

- 账户 ID 唯一；
- `(account_id, decision_id)` 意图唯一；
- `(account_id, order_id)` 订单唯一；
- `(account_id, order_id, fill_sequence)` 成交唯一；
- `(account_id, session)` 每日快照唯一。

数据库迁移只能新增表，不重写现有 Futu 订单和事件。

## 9. CLI、HTTP 与页面

CLI 增加：

- `pte account list`
- `pte account create --account-id ... --name ... --baseline ... [--initial-cash ...]`
- `pte account pause --account-id ...`
- `pte account resume --account-id ...`

HTTP 状态接口返回渠道账户、虚拟账户列表、选中账户详情和共同区间比较数据。写接口只提供单账户暂停/恢复；首版不提供删除、重置资金或修改基线，避免破坏前瞻账本。

页面分为：

1. 渠道验证区：保留 Futu 健康、账户、订单、成交和全局运行状态；
2. 虚拟账户区：账户卡片、策略身份、净值、收益、最大回撤、卡玛比率、盈亏比、持仓和运行开关；
3. 账户详情区：决策、订单、成交、现金变化、流动性告警和结构化诊断；
4. 比较区：明确展示共同观察区间，重点比较最大回撤、卡玛比率和盈亏比，收益率作为辅助指标。

状态字典使用语义准确的中文，结构化对象使用格式化渲染，不展示裸 JSON。

## 10. 错误处理与安全

- 基线版本、哈希或 execution 配置不匹配：账户进入阻塞状态，不生成订单；
- 数据未发布、清单校验失败或有效交易日缺失：保持原账本并告警；
- 重复运行：通过唯一约束幂等收敛；
- 虚拟成交结算异常：事务回滚，不产生半笔成交；
- Futu 断线或账户查询失败：渠道进入降级状态并退避重试，虚拟账户继续运行；
- Futu 环境继续硬锁 `TrdEnv.SIMULATE` 和中国市场；
- 任何渠道回报未明确给出成交数量时，不改变渠道持仓；
- 暂停不撤销活动订单，撤单继续采用二次确认；
- watchdog 和系统服务继续保活同一个 PTE 进程，无需为每个虚拟账户启动进程。

## 12. 验收标准

- 生产 advice 只需一个完整基线身份即可生成确定性订单；
- 不存在可运行的“基线版本 × 执行规则版本”组合入口；
- 持仓周期内目标数量稳定，价格改善不会触发连续加仓；
- 回测、虚拟账户和 advice 都遵守100份整数倍、0.001价格档位和相同费用口径；
- 触价但未穿价不会被记为确定成交；
- 两个虚拟账户可使用不同完整基线同时运行，资金、订单、成交和快照相互隔离；
- 单账户暂停不影响其他虚拟账户和 Futu 对账；
- Futu 断线不阻塞虚拟账户，连续同类错误不会形成高频事件风暴；
- PTE 重启后恢复全部账户、活动订单和周期目标，不重复生成订单或成交；
- 页面能区分渠道成交与模型成交，并按共同观察区间比较核心指标；
- 新完整基线在截至2026-09-02的开发池完成审计，审计结果不覆盖历史实验；
- 聚焦测试、Python 编译和 `git diff --check` 通过。
