# Paper Trading Engine 观测与干预设计

## 目标与范围

在同一仓库新增独立 Python 包 `paper-trading-engine`（PTE），持续运行
`SH.588080` 模拟交易并提供本机观测与干预页面。首版完成全部 P0：运行身份、
健康状态、最新决策、账户对账、订单生命周期、自动提交、暂停/恢复、二次确认
撤单、重启恢复、告警和审计。样本外收益比较留到 P1。观察从 2026-09-01
收盘信号、2026-09-02 首次执行开始。

首个渠道为 Futu，但 PTE 的领域模型和页面只使用通用的账户、持仓、订单、成交
和渠道健康概念。运行硬约束为模拟环境、中国市场、`SH.588080`、DAY 委托和
100 份整数倍。缺少实时行情权限标记为 `DEGRADED_QUOTE`，仍允许自动提交。

## 边界与依赖方向

`czsc_trader` 拥有数据校验、活动基线解析、信号计算、执行规则和订单定价；PTE
拥有持续调度、渠道接入、幂等提交、状态持久化、页面与人工干预。两者是同仓库
并列分发包和独立进程，依赖方向固定为：

```text
data prepare job -> validated repository artifacts
PTE -> czsc-trader advice run (subprocess JSON contract)
PTE -> BrokerGateway -> Futu SIMULATE
UI -> PTE application service -> SQLite/BrokerGateway
```

PTE 不导入 `czsc_trader.*`，也不直接调用 Tushare。Futu 适配器不生成价格、
不改变数量、不以其他价格重试。所有子进程调用使用参数数组、UTF-8、显式
`--repo-root` 和超时，不经 shell。

代码结构：

```text
packages/paper_trading_engine/
├── pyproject.toml
├── src/paper_trading_engine/
│   ├── contracts.py
│   ├── advice_client.py
│   ├── store.py
│   ├── engine.py
│   ├── futu_gateway.py
│   ├── web.py
│   └── cli.py
└── tests/
```

运行态固定在 `state/paper_trading/runtime.db`，不进入版本控制。

## Advice CLI 契约

PTE 调用：

```text
czsc-trader advice run --symbol 588080.SH --asset etf \
  --actual-quantity 20000 --position-size 50000 \
  --repo-root <absolute-path> --format json
```

`actual_quantity` 是已成交持仓，`position_size` 是满仓目标份数。策略目标为 1 时
`target_quantity=position_size`，目标为 0 时为 0；`delta_quantity` 等于目标减
实际。正数生成 BUY，负数生成 SELL，零生成 WAIT/HOLD。旧
`--actual-position/--quantity` 暂时保留兼容，但 PTE 只用新契约。

成功结果包含 `contract_version="advice.v1"`、确定性的 `decision_id`、
`valid_session`、三个数量字段、活动基线和执行规则版本及哈希、信号参考价、
未复权执行参考价，以及可直接提交的订单字段：`side`、`quantity`、
`order_type="LIMIT"`、数值 `limit_price`、`time_in_force="DAY"`。相同输入产生
相同 `decision_id`。stdout 只输出一个 JSON 文档，诊断写 stderr；PTE 拒绝未知
契约版本、非数值价格或违反硬约束的订单。

买价按冻结 entry policy 计算。卖出保护价由项目配置的跌停比例和 tick 明确计算，
并写入执行规则身份；任何渠道端自动调价均关闭。委托被拒后记录告警，不使用
券商返回规则重新定价。

## 引擎、一致性与恢复

每轮先拉取账户、持仓和当日订单，再调用 advice。提交前先持久化 `OrderIntent`，
以 `decision_id` 作为业务幂等键，并把 `intent_id` 写入渠道 remark。数据库或渠道
已存在对应委托时不重复提交。渠道推送先于下单响应也通过 remark 合并到同一订单。
只在 `valid_session` 当天允许新单；其他日期保留观测并告警。标的存在任何未终态
订单时也不创建新单，避免部分成交改变实际数量后重复覆盖剩余委托。

订单状态采用至少一次事件收敛：渠道订单号和状态可重复写入，累计成交数量只能
单调增加；只有明确累计成交回报形成成交增量，委托受理不改变持仓。重启后必须
完成账户、持仓和活动订单恢复，才允许提交新单。

暂停只阻止新订单，已有订单继续轮询和对账。恢复要求最近一次对账成功。撤单令牌
单次使用、短时有效且绑定渠道订单号；撤单必须经过令牌确认。所有状态变更、异常、
提交与人工操作追加到审计事件表。

## 页面与运行

`pte serve` 启动协调循环和仅监听 `127.0.0.1` 的页面；`pte once` 执行一轮，便于
诊断与调度。页面每五秒获取状态，显示环境硬锁、渠道健康、活动基线、数据截止、
决策、目标/实际仓位、现金/资产/冻结资金、活动订单、最近事件和告警，并提供暂停、
恢复、获取撤单令牌和确认撤单操作。页面不直接访问数据库或渠道。

## P0 验收

- advice v1 对数量差、确定性身份、项目侧买卖限价和错误码有契约测试。
- 内存渠道验证硬锁、幂等、成交增量、暂停语义、撤单确认和重启恢复。
- Futu 假上下文验证 SIMULATE/CN/DAY/白名单参数以及关闭自动调价。
- HTTP 测试覆盖状态、暂停、恢复和两步撤单。
- 真实 Futu 只做只读启动验证；不重复既有 100 份提交—撤单探针。

## 已冻结并完成的 P0 优化

- 拆分运行调度频率：订单状态和成交回报保持约 5 秒轮询；账户与持仓降低为
  30～60 秒；策略 advice 只在完整收盘数据发布或数据身份变化后计算一次。只有
  出现新的 `decision_id` 才进入自动提交判断，避免日频策略每 5 秒重复计算和查询。
- 表现层建立精准的中文语义映射，将环境、健康度、运行状态、动作、订单状态和
  告警等英文枚举转换为中文展示；底层契约与持久化字段继续使用稳定英文值。
- 账户、最新决策、订单和事件采用字段化卡片、表格与格式化详情展示，页面不直接
  显示裸 JSON；诊断信息仍可通过可展开区域查看格式化 JSON。
- 修复“恢复运行”按钮点击后无可见反馈的问题。已覆盖暂停后的点击链路，分别
  验证浏览器请求、HTTP 响应、引擎状态和页面刷新；成功、失败都必须给出明确反馈。
- 完整收盘数据存放在忽略版本控制的运行目录，由每日 16:15 后的数据发布任务更新；
  发布失败写入审计告警并退避重试。
- 下一有效交易日来自 Tushare SSE 交易日历并固化在执行数据清单中，advice 直接消费
  固化日期，避免把周末、节假日或调休按普通工作日推断。
